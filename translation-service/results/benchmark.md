# Hy-MT2-1.8B Q4_K_M 本地实测

环境：Apple M1 Pro（10 核）、32 GB 内存，llama.cpp `b12140`，Node.js `24.13.1`。使用腾讯官方 Q4_K_M 权重，已核对 SHA-256。模型进程配置 4 个推理槽、8 个 CPU 线程、8,192 总上下文。Metal 使用本机 GPU，纯 CPU 使用 `--n-gpu-layers 0`。

延迟从客户端发出请求到收到完整 HTTP 响应，包含服务和推理的等待时间。p50 为中位数，p95 为第 95 百分位数。短字幕为 8 条、每条 54–85 个字符；段落为 4 段、每段 280–324 个字符，性能测试均为英译简中。每组固定在途请求数，有空位就发下一条。模型已预热，未使用译文缓存，也未复用跨请求的提示 token。

| Metal | 在途请求 | 首轮 p50 / p95 | 首轮请求/秒 | 复测 p50 / p95 | 复测请求/秒 |
|---|---:|---:|---:|---:|---:|
| 短字幕 | 1 | 244 / 329 ms | 3.98 | 235 / 301 ms | 4.29 |
| 短字幕 | 2 | 459 / 2,144 ms | 3.02 | 437 / 649 ms | 4.48 |
| 短字幕 | 4 | 679 / 977 ms | 5.90 | 669 / 1,011 ms | 5.89 |
| 段落 | 1 | 801 / 961 ms | 1.20 | 748 / 849 ms | 1.31 |
| 段落 | 2 | 1,508 / 1,602 ms | 1.34 | 1,507 / 1,580 ms | 1.33 |
| 段落 | 4 | 1,750 / 2,167 ms | 2.18 | 1,855 / 2,414 ms | 2.07 |

两次 Metal 压测各 144 条计时请求，全部完成且未截断。首轮短字幕并发 2 时有两次响应超过 2 秒，复测未重现。

纯 CPU 每组测两轮，72 条计时请求均完成且未截断。段落每组只有 8 条，p95 等于组内最大值，主要供排查抖动参考。

人工检查了 16 条样例，包括英译简中、日语、西语、阿语及中译英。以下是未经润色的首轮 Metal 结果：

| 源文片段 | 模型译文片段 | 观察 |
|---|---|---|
| Oh, great. Another meeting that could have been an email. | 哦，太好了。又一场本可以通过邮件沟通的会议。 | 保留反讽。 |
| The price rose by 3 percentage points, not by 3 percent. | 价格上升了3个百分点，而不是3%。 | 正确区分百分点与百分比。 |
| a tiny dip in starlight | 星光中的微小变化 | 漏掉亮度下降的方向。 |
| after they had both warmed up | 在两台机器都加热之后 | 性能测试语境下应译为“预热”。 |

完整源文在 [`samples.json`](../benchmarks/samples.json)。运行基准脚本可生成逐条 JSON，含原始译文、请求延迟及模型计时。样例由人工编写，结论不代表各语种的一般准确率；短时间压测也不能直接推算 VPS 或线上高峰容量。

按 1,000 人每天各观看 2 小时、每 3 秒送一次翻译、每次都需要新推理估算，全天平均约 28 请求/秒，已超过这台机器测到的短字幕吞吐。实际部署前应以真实字幕为输入，量出每视频每目标语言的复用率、预取后实际送出的请求数和高峰等待时间。
